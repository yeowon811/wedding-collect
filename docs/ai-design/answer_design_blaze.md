# AI 상담 답변 설계 (Blaze 전제, 2026-11-20 초안)

지금 구조를 잊고 처음부터 다시 정한 안. 11-20 피드백(좁은 범위부터, 웹 보충 조사, Gemini가 형식 결정, 글은 최소) 반영. 형식 규칙은 `answer_format_rules.md`. 아래 예상 답의 숫자·이름은 `assets/data`의 실제 값(11-19 수집)으로 채웠고, `{N}`은 구현 때 앱이 계산할 값.

## 0. 전제 (Blaze로 바뀌면 달라지는 것)

| | 지금 (무료) | Blaze |
|---|---|---|
| Gemini 한 번 | 10~20초, 자주 시간 초과 | 1~3초 예상 |
| 하루 한도 | 평가 몇 번이면 소진 | 사실상 걱정 없음 (예산 알림만) |
| 질문 1개 비용 | 0원 | 약 7~15원 |
| 그래서 | 답 다시 쓰기 끔, 규칙으로 버팀 | **질문 이해와 답 작성 모두 Gemini에 맡기고, 앱은 조회·판정·검사** |

## 1. 새 흐름

사용자 피드백 (11-20) 세 가지를 반영:
- **좁은 데서 시작해 넓혀 가기:** 내가 고른 구 → 맞닿은 구 → 시 전체 → 가까운 시도. 단계마다 "더 넓혀 볼까요?"로 선택지를 늘린다
- **규칙 안에만 가두지 않기:** 앱 데이터에 없으면 되묻고(어느 역?), Gemini가 Google 검색·지도·URL 읽기로 직접 찾아 비교해 준다
- **형식은 Gemini가 정함:** 기본 틀은 있지만 질문에 더 맞는 형식을 Gemini가 고르면 그게 우선

```
질문
 ① 이해 (Gemini, 함수 호출)
    → 도구 + 조건 + 자기 정보 + 빠진 정보(되물을 것)
    → 꼭 필요한 정보가 빠졌으면 여기서 되묻기 (예: "어느 역 기준으로요?")
 ② 조회·판정 (앱)
    → 앱 데이터 검색, 정책 판정, 계산, 예약 달력. 범위는 좁은 데서 시작
    → 결과마다 ID가 붙은 사실 묶음 + "비어 있는 값" 목록
 ③ 보충 조사 (Gemini + Google 검색·지도·URL 읽기, 필요할 때만)
    → 앱 데이터 밖 질문만 (역 위치, 공고 기간, 주변 숙소 등). 예식장의 비어 있는 값은 채우지 않고 문의 안내 (R2)
    → 찾은 값마다 출처 URL·찾은 날짜. 위치는 좌표만 받고 거리는 앱이 계산
 ④ 답 작성 (Gemini, JSON)
    → 블록을 골라 배치 (아래 2장). 앱 데이터와 웹 정보는 다른 블록·표시로
 ⑤ 검사 (앱 규칙 + Gemini 검토, 3-2장)
    → 조건 충족·숫자 출처·직전 답과 중복·빈 값 안내·형식 (앱)
    → 질문 부합·범위·맥락·반복 (Gemini 검토)
    → 걸리면 고칠 점을 붙여 ④ 한 번 더 → 또 걸리면 기본 틀 템플릿
```

질문 1개에 Gemini 3~5번 (이해·작성·검토 + 필요할 때 보충 조사·다시 쓰기). Google 검색·지도는 별도 요금이 있어 ③은 필요할 때만.

## 2. 답 형식: 글은 최소, 나머지는 보이게

규칙 F1~F14는 [answer_format_rules.md](answer_format_rules.md) (Google·Alexa·Salesforce·Microsoft·NN/g·Perplexity·토스 가이드에서 모음). 목표: **3초 안에 답이 보이는 화면.**

### 블록 (Gemini는 이 목록에서만 고름, F11)

| 블록 | 화면 | 글자 제한 | 값은 누가 |
|---|---|---|---|
| `headline` | 굵은 답 한 줄 + 배지 0~2개 ("모두 무료", "120명 가능 2곳") | 제목 20자 안팎, 배지 10자 | 제목 Gemini, 배지 숫자는 앱 |
| `text` | 설명 한 문장 (없어도 됨) | 40자 안팎, 1문장 | Gemini |
| `filters` | 적용된 조건 칩 (✕로 빼기, + 조건) | 칩 10자 | 앱 (도구 조건에서) |
| `cards` | 카드 최대 3개. 1줄: 이름 + 맞는지 배지 / 2줄: 핵심 값 3개 | 이유는 첫 카드에만 15자 (생략 가능) | 값·배지는 앱, 이유는 Gemini |
| `table` | 비교표 (행 최대 5) | 칸 값만 | Gemini가 ID·칸을 고르면 앱이 채움 |
| `ranking` | 순위 3개 (거리순, 빈 날 많은 순) | 항목당 한 줄 | 앱 계산 |
| `steps` | 단계 최대 4개 | 단계당 15자 | Gemini, 날짜는 앱 |
| `budget` | 금액 표·합계 | 숫자만 | 앱 계산 |
| `ask` | 되묻기 한 문장 + 선택 칩 | 질문 30자 | Gemini |
| `web` | 웹에서 찾은 값 + 출처 링크 | 한 줄 | Gemini(검색), 출처 필수 |
| `next` | 다음 행동 칩 최대 4개 (좁히기·넓히기·다음 할 일) | 칩 12자 | Gemini |
| `fold` | 접힌 한 줄: "출처 보기 · 어떻게 찾았나요" | 고정 문구 | 앱 |

`caution` 블록은 없앰: 대상 아님·정보 없음·바뀔 수 있음은 **카드 배지**로 보이게 하고(F10), 카드 밖 주의가 꼭 필요할 때만 `text` 한 문장으로.

### 배지 색 (모든 카드 같은 규칙)
| 색 | 뜻 | 예 |
|---|---|---|
| 초록 | 내 조건에 맞음 | 120명 OK · 5/15 오전 빔 · 대상 |
| 주황 | 확인 필요 | 정보 없음 · 조건 확인 · 웹 정보 |
| 회색 | 맞지 않음 | 80명까지 · 대상 아님 · 예약 마감 |

### 카드 두 줄 (F6, 항목 순서 고정)
| 종류 | 1줄 | 2줄 |
|---|---|---|
| 예식장 | 이름 + 배지 | 구 · 정원 · 대관료 (· 질문에 따라 주차/날짜) |
| 정책 | 이름 + 배지(대상/조건 확인/대상 아님) | 기관 · 지원 내용 · 금액 |
| 업체 | 이름 + 배지(예산 안/초과) | 항목 · 가격 · 평점 |
| 할 일 | 할 일 + 배지(급함/여유) | 마감일 · D-n |

### Gemini가 돌려줄 형식
```json
{"blocks": [
  {"type": "headline", "title": "강남구 공공예식장 4곳", "badges": ["all_free", "fit_count"]},
  {"type": "filters"},
  {"type": "cards", "ids": ["H080", "H078", "H081"], "reason": {"H080": "인원 여유가 가장 큼"}},
  {"type": "next", "items": ["송파·서초까지", "서울 전체", "5/15 빈 곳"]},
  {"type": "fold"}
]}
```
배지는 앱이 아는 종류(`all_free`, `fit_count`, `open_count` …) 중에서 고르고 숫자는 앱이 채움.

기본 틀 (Gemini 실패·지연 시): `headline` → `filters` → `cards` → `next` → `fold`

### 앱이 강제하는 것
- 제목·설명·칩 글자 수를 넘으면 다시 쓰게 함 (K5)
- 제목에 쓴 숫자가 설명·카드 이유에 또 나오면 다시 쓰게 함 (F14)
- 블록 순서: `headline` 또는 `ask`가 항상 첫 블록 (F1)
- 문장 2개 초과 금지 (headline 제외, F2)

## 3. 규칙

정보는 세 단계로 구분해 답에 표시한다.

| 출처 | 표시 | 예 |
|---|---|---|
| 앱 데이터 | 수집 날짜 | 정원, 요금, 예약 달력, 정책 원문 |
| 웹에서 찾은 정보 | "웹에서 찾은 정보 · 출처 링크 · 확인 필요" | 역 위치·거리, 공고 기간 (예식장 빈 값은 채우지 않음) |
| 일반 지식 | "일반 안내" | 답례 관례 |

| # | 규칙 | 누가 |
|---|---|---|
| R1 | 앱 데이터에 값이 있으면 그 값이 우선. 문장 속 숫자는 앱 결과나 출처 있는 웹 결과에 있어야 통과 | 앱 검사 |
| R2 | 예식장·정책의 비어 있는 값(정원·요금·주차 등)은 지어내거나 웹으로 채우지 않고 "현재 정보가 없어요. 문의로 확인해 주세요" + 그곳의 문의처(전화·예약 페이지, 240곳 모두 있음). 웹 조사는 앱 데이터 밖 질문(역 위치, 공고 기간 등)에만 | 앱 (문구 고정) |
| R3 | 정책 대상 여부는 `policy_matcher` 판정. 웹 원문은 근거로 보여 주기만 | 앱 |
| R4 | 계산(식대 × 인원, 날짜, 거리, 합계)은 앱이 하고 AI는 결과만 인용 | 앱 |
| R5 | 일반 지식은 "일반 안내" 표시 | Gemini + 앱 표시 |
| R6 | 사용자가 자기 이야기로 말한 값만 내 정보에 저장 + [되돌리기] | Gemini 추출 + 앱 근거 검사 |
| R7 | 이름·전화·이메일은 Gemini·검색에 보내기 전에 가림. 검색어에는 장소·정책 이름만 | 앱 |
| R8 | 후속 질문("그중에", "말고")은 앱이 앞 조건과 합침 | Gemini 표시 + 앱 합침 |
| R9 | 범위는 좁은 데서 시작(내가 말한 구 → 내 시군구 → 맞닿은 구 → 시 전체 → 가까운 시도), 넓히기는 `next`로 제안 | 앱 + Gemini |
| R10 | 답에 꼭 필요한 정보가 빠졌으면 먼저 되묻기(`ask`). 없어도 답할 수 있으면 답하고 `next`로 좁히기 제안 | Gemini |
| R11 | 예약 현황은 "11/19 수집 기준, 바뀔 수 있어요" | 앱 |
| R12 | 실제 업체 가격은 웹에서 찾았어도 출처 없으면 넣지 않음 | 앱 검사 |
| R13 | Google 검색을 쓴 답은 검색 제안을 화면에 표시 (Google 이용 조건) | 앱 |
| R14 | Gemini 실패·지연이면 기본 틀 템플릿으로 답함 | 앱 |

## 3-2. 답 검사 (질문 수가 적으니 느려도 확실하게)

답을 내보내기 전에 세 겹으로 검사한다. 질문이 많지 않아 질문당 Gemini 1번이 더 늘어도 괜찮다(약 +5원, +1~2초).

### 가. 앱 검사 (항상, 규칙)
| # | 검사 | 실패하면 |
|---|---|---|
| K1 | **조건 충족:** 카드마다 질문 조건을 실제로 만족하는지 (고른 구·시도 안인지, 무료만이면 요금 0인지, 하객 수 ≤ 정원인지, 날짜 질문이면 그날 공석인지, 제외한 구가 없는지) | 그 카드 빼기, 남은 게 없으면 "조건에 맞는 곳이 없어요" + 넓히기 제안 |
| K2 | **숫자·이름 출처:** 문장 속 숫자·예식장 이름이 조회 결과(또는 출처 있는 웹 결과)에 있는지 | 그 문장 빼고 다시 쓰기 |
| K3 | **직전 답과 같은지:** 카드 ID 묶음과 결론 문장이 바로 앞 답과 같은지 | 후속 질문인데 결과가 같으면 다시 쓰기 지시("조건을 바꿔도 결과가 같다는 걸 먼저 말하기"), 같은 질문 반복이면 그대로 두되 "앞과 같은 결과예요" |
| K4 | **빈 값 안내:** 답이 비어 있는 값을 언급할 때 "현재 정보가 없어요 · 문의" 문구와 문의처가 있는지 | 앱이 붙임 |
| K5 | **형식 (F1~F14):** 첫 블록이 `headline`·`ask`인지, 제목 20자·설명 1문장·칩 12자·칩 4개·카드 3개 이내인지, 제목 숫자를 다시 쓰지 않았는지, 허용 블록만 썼는지 | 다시 쓰기 |

### 나. Gemini 검토 (항상, 답 쓴 모델과 다른 지시문)
질문 · 직전 2턴 · 도구 조건 · 조회 결과 요약 · 답 블록을 주고 JSON으로 판정만 받는다.
```json
{
  "answers_question": true,      // 질문에 직접 답했나 (물은 게 '몇 곳'이면 개수가 있나)
  "scope_ok": true,              // 질문이 말한 범위(구·날짜·조건)를 그대로 썼나, 넓히거나 좁히지 않았나
  "context_ok": true,            // 후속 질문이면 앞 조건을 이어받았나 / 새 질문이면 앞 조건을 버렸나
  "repeats_previous": false,     // 앞 답과 내용이 사실상 같나
  "unsupported_claim": [],       // 조회 결과에 없는 주장
  "missing": [],                 // 질문이 요구했는데 빠진 것
  "fix": ""                      // 고칠 점 한 줄
}
```
- 하나라도 걸리면 `fix`를 붙여 답 작성 1번 다시 → 다시 검사 → 또 걸리면 기본 틀 템플릿
- 판정과 이유는 답 아래 '검사 기록'(개발용, 시연 때 펼쳐 보여 줄 수 있음)에 남김

### 다. 평가 (개발할 때, 배포 전마다)
| 평가 | 방법 | 결과 |
|---|---|---|
| 정답 검사 | 예상 질문 52 + 탐색 36에 질문별 기대값(구·개수·포함/제외 ID·대상 여부) → 앱이 자동 채점 | 맞음/틀림 표 |
| 이전과 비교 | 이번 답과 지난 평가 답을 질문별로 나란히 → 카드 ID·숫자·판정이 바뀐 질문만 모음 | "바뀐 질문 n개" 보고서 (좋아졌나/나빠졌나 확인) |
| 같은 답 반복 | 대화형 시나리오(후속 질문 연속)에서 연속 두 답이 같은지 | 반복 n건 |
| 흔들림 | 같은 질문 3번 → 카드 ID·결론이 다른지 | 흔들린 질문 목록 |
| 판정 모델 | Gemini 검토(나)와 같은 기준으로 전 질문 채점, 사람이 틀린 판정만 확인 | 질문 부합률 |

보고서는 `docs/ai-eval/`에 날짜별로 남겨, 소개서의 "오류·불확실성 대응"(5점) 근거로 쓴다.

## 4. 질문별 예상 답

공통 가정 (내 정보): 서울 강남구 · 만 29세 · 예식일 2027-05-15(토) · 하객 120명 · 무주택 · 예산 3,000만원. 오늘 2026-11-20.

표기: `제목` 굵은 한 줄 · `배지` · `설명` 한 문장 · `조건` 칩 · `카드` 1줄/2줄 · `칩` 다음 행동 · 맨 아래 접힌 줄(출처 보기 · 어떻게 찾았나요)은 모든 답에 있으므로 생략. 초록·주황·회색은 배지 색.

### A. 시작

**A1. (상담 시작)**
```
제목  무엇부터 알아볼까요?
설명  입력하신 정보(서울 강남구 · 하객 120명)로 답해 드릴게요.
칩    받을 수 있는 정책 · 강남구 예식장 · 5/15 빈 곳 · 뭐부터 해야 해?
```

### B. 예식장 찾기

**B1. "공공예식장 추천해줘"** → `search_venues` (내 시군구부터, R9)
```
제목  강남구 공공예식장 4곳
배지  모두 무료 · 120명 가능 2곳
```

## 5. 정한 것 / 남은 것

정함 (11-20)
- 답 작성은 Gemini, 형식(블록 배치)도 Gemini가 정하고 기본 틀은 대비용
- 범위는 좁은 데서 시작해 넓히기를 제안
- 예식장·정책의 빈 값은 "현재 정보 없음 · 문의" + 문의처. 앱 데이터 밖 질문은 되묻고 Google 검색·지도·URL 읽기로 보충 (출처 필수)
- 형식 규칙 F1~F14 적용: 제목 한 줄 + 배지 + 카드 두 줄 + 칩, 글은 두 문장까지
- 답마다 앱 검사 + Gemini 검토, 걸리면 한 번 다시 쓰기. 배포 전 평가에 이전 답 비교·반복·흔들림 검사

남음
1. 카드 "고른 이유"를 AI가 쓸지, 정해진 문구로 쓸지
2. 정책 답에서 "조건 확인 필요" 정책을 카드에 섞을지
3. 검색·지도 요금 단가 확인 후 하루 사용 한도
4. `table`·`ranking` 블록의 칸(필드) 목록 확정
